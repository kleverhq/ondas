# Reduce cold full-range VCD selected-history cost

This ExecPlan is a living document. Update Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective at each milestone; add a change note at the bottom whenever the plan changes. Remove this temporary task directory before merging into `main`, after promoting durable backend conclusions to `docs/vcd-native.md` and durable benchmark policy to `docs/benchmarking.md` if needed.

## Purpose / Big Picture

Issue #33 reports that the first full-range trace of nine SCR1 AXI VCD signals takes about three seconds *after* opening, despite issue #31 making opening fast and issue #32 fixing late narrow queries. The nine traces contain 1,286,446 observations. Make the same exact query and complete streaming scans materially faster without shifting work into `open()`, accepting malformed files, losing event multiplicity, or silently changing the bounded-memory and early-break contracts. First commit a public, locked-fixture benchmark and measure the unfixed code; only then change the reader. A fresh standalone query on the issue's converted public SCR1 AXI FST is the end-to-end check.

## Non-Goals

Do not alter Wavepeek, the public fixture provider, sibling repositories, or private assets. The locked persistent benchmark can use the existing SCR1 **AHB** VCD, which exercises the same full-body parser but is not the issue's AXI artifact. Do not describe its timing as the original AXI timing. No new dependency, opening-time history cache, automatic data download, or CI timing threshold is warranted. Do not change FSDB/FST semantics.

## Surprises & Discoveries

- The published locked `fst0022-scr1-max-axi-coremark` FST (`6280b6d9…`) differs in its FST checksum from the issue's rtl-artifacts release FST (`14130025…`), but `fst2vcd` produces the same 953,668,940-byte size and **identical value-change body** (`fe2c56dc…`). Only the VCD header's `$date` differs. Therefore the exact original release artifact stays the standalone reproduction while the locked provider remains usable as a control; neither body hash alone nor an empty oracle proves trace correctness.
- The present cold late-query fast path in `src/query/engine.rs::read_ticks_from` only prepares a small selected-state prefix when a range starts after tick zero. A full-range query starts at zero and instead rereads almost one gigabyte serially. Nine AHB control signals yield 2,365,644 records in ~3.06 s, a useful locked-fixture workload but not an AXI result. Even tracing only the original AXI `axi_rst_n` (two records) still takes ~3.13 s, isolating the bottleneck to serial body traversal rather than history copying or callback cost.
- One channel batch per chunk left all workers blocked until their turn: the original nine-history trace still took 2.57 s. Increasing the bounded in-flight queue to 24 batches per worker (about 192 MiB across workers before allocator overhead) let independent parsers run concurrently: original AXI ~0.7 s traces / ~0.65 s scans; locked AHB Criterion ~1.50 / 1.49 / 1.48 s for traces/scan/candidates versus 3.14 / 3.00 / 2.98 s before. Inlining one-bit selected values removed millions of worker-side heap allocations and improved the original AXI trace from ~0.92 to ~0.7 s without changing public values. The extra transient memory is disclosed in `docs/vcd-native.md`.
- Preliminary independent Astra Medium reviews found two real boundary problems: the last unflushed selected batch was lost on parser errors, and sparse workers kept reading after a callback stopped the scan. Ordered flushing before error delivery and a shared positional-read cancellation flag resolve them. Final correctness review found a narrower sparse-stop gap: flushing a fixed number of early selected records does not guarantee a tick transition when multiple records share one timestamp. Flush the first timestamp transition instead. An attempted test-only positional-byte counter asserted how much of the first chunk was consumed after `Break`, but thread scheduling could let a correct worker finish the chunk before the consumer sets cancellation. The assertion was removed as a potential CI flake. A subsequent read-only review found that a first selected record in the *next* chunk can complete a pending tick from the preceding chunk; flushing only that worker's first timestamp transition still delays the callback. Flush the first selected record as well as its first transition. A deterministic private flush-policy test covers both triggers, a forced cross-chunk sparse scan checks the observable `Break`, and the low-level cancellation test covers reads after `Break`. Cancellation never bypasses eager opening validation.

## Decision Log

- Decision: Commit public benchmark coverage and capture a before-fix Criterion baseline *before* any reader changes, as requested. Rationale: separating opening, selection, and iteration time prevents an opening-time regression from masquerading as a fix. Date/Author: 2026-09-26, main session.
- Decision: Keep the exact rtl-artifacts SCR1 AXI VCD under ignored `tmp/issue33/` and use existing locked AHB VCD for the permanent benchmark. Rationale: editing/publishing a sibling fixture provider requires separate authorization and the existing public AHB file already exercises the same large VCD reader; label the distinct waveforms explicitly. Date/Author: 2026-09-26, main session.
- Decision: Prototype bounded per-chunk **batch** delivery of selected records from parallel `Reader::walk` workers, consumed in source order by the existing shared query engine. Rationale: a one-signal/two-record query still costs ~3 s, proving full-body serial parsing is the shared bottleneck. Batching avoids the known regressing per-record channel design, and a bounded channel per chunk prevents unbounded scan memory growth. Fall back to serial before any callback if startup fails. Date/Author: 2026-09-26, main session.
- Decision: Budget approximately 192 MiB of transient batch payloads across file workers, excluding allocator overhead, and inline one-bit values within private worker records. Rationale: a one-batch queue serialized most of the parsers on dense histories; 24 bounded batches per chunk enabled a 3–4× improvement on original AXI while avoiding an unbounded whole-history cache. The memory trade-off is disclosed and the worker queue is fixed-size. Date/Author: 2026-09-26, main session.
- Decision: Flush pending selected records before a worker reports an error and cancel remaining workers promptly after a visitor `Break` or error. Rationale: serial replay can emit/stop on selected records preceding malformed input; asynchronous queues cannot silently discard that prefix or keep sparse workers reading whole chunks after the caller stops. Date/Author: 2026-09-26, main session.
- Decision: Flush the first selected record and the first selected timestamp transition per worker, then use only bounded batch-size flushes. Rationale: a fixed count of initial records may all share a tick, delaying its completion, while the first record of a new chunk may itself complete a pending tick from the preceding chunk. Both triggers are needed for prompt early `Break` without sacrificing batching. Date/Author: 2026-09-26, main session.
- Decision: Delete a scheduler-dependent test-only positional-byte assertion and its counter instead of building synchronization machinery solely to measure read-ahead in a self-contained test. Rationale: even correct workers may finish parsing before the consumer is scheduled, making the assertion flaky. The observable sparse `Break` and low-level cancellation behavior remain covered without a timing gate. Date/Author: 2026-09-26, main session.

Preliminary findings were fixed before that commit; its final correctness review identified one residual same-tick early-stop gap. A scheduler-sensitive test assertion was removed; the final follow-up `806180d` flushes both the first selected record and the first selected timestamp transition per chunk. Its deterministic focused tests, unchanged AXI observation hash, matched locked AHB performance controls, clean-tree full CI/MSRV/doctests and final read-only review all passed. The goal is a material reduction from roughly three seconds on the exact AXI nine-history query, with no first-open or narrow-query regression. Wellen's ~14 ms selected-history load is a different API/representation and is a diagnostic, not a promised equal-speed target.

## Context and Orientation

`src/waveform.rs::Waveform::traces` creates a fresh `Selection` and forwards to `src/query.rs::Selection::traces`; its `scan_each` collects owned results via callback. `src/query/engine.rs::Selection::read_ticks_from` normalizes records by timestamp and signal, handles entering values, event counts, duplicate selections and change times, and asks `src/backends/vcd.rs::Reader::read_from` for raw records. The VCD reader validates the entire body eagerly during `Reader::open` and retains safe Unix same-file chunk boundaries and a serial replay reader. Issue #32 uses selected-prefix summaries for late narrow queries, but not full-range scans starting at tick zero. `benches/vcd.rs::scr1` currently benchmarks opening, a narrow scan and points using locked public `vcd0097-scr1-max-ahb-coremark`; `tests/support/fixtures.rs` checks its SHA-256. The original AXI artifact is *not* that fixture. `docs/vcd-native.md` describes the streaming and opening contracts.

## Open Questions

The bounded batch reader improves both SCR1 inputs and preserves checked ordering. Its ~192 MiB transient selected-batch budget (plus worker buffers and allocator overhead) is explicit. Cancellation, partial-error precedence, same-tick and cross-chunk early stops passed focused tests, clean-tree CI and final read-only review. No technical gate remains; publication and the issue report are separate operational steps.
